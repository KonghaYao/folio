# Folio 大画布性能与容量实测

## 浏览器整体验收

同一台 Linux x86-64 主机、同一份确定性数据、Bun 1.4.5、Chromium 158.0.8127.0。下表箭头左侧是完成 Peri Chat 时的原版，右侧是调优版。每次启动独立服务、SQLite 库和浏览器配置，用正常 HTTP 操作写入对象，然后在可见画板上滚动、缩放、下笔，另一台设备通过只读分享进入。每组结束后逐条核对原始对象 SHA-256，以及双方新增笔迹的坐标、压力和倾角。

| 混合对象 | 冷开可编辑画板，秒 | 全图平移帧间隔 P95，ms | 全图平移估算丢帧率 | 落笔至另一端对象计数更新，ms | 刷新可编辑，秒 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 0.20 → 0.19 | 16.8 → 16.8 | 3.2 → 1.1% | 453 → 456 | 0.10 → 0.11 |
| 10,000 | 0.46 → 0.49 | 100.1 → 16.8 | 69.4 → 1.1% | 461 → 451 | 0.28 → 0.13 |
| 50,000 | 1.80 → 1.14 | 275.1 → 16.7 | 85.9 → 1.1% | 535 → 453 | 0.90 → 0.47 |
| 100,000 | 2.65 → 1.95 | 333.4 → 16.8 | 87.8 → 0.0% | 797 → 456 | 2.08 → 0.64 |

1,000 和 10,000 对象每版各跑一次。50,000 和 100,000 每档交替跑原版、调优版、调优版、原版。每个手势先用逐帧时间计算本次 P95，再取同一版本两轮 P95 的中位数。冷开时间取浏览器导航至画板就绪后的绘制机会。100,000 对象冷开后首次**截图确认**内容可见的耗时为 4.32 → 2.30 秒，包含截图操作的开销。1 万对象冷开单次多耗时约 34 毫秒，1 千对象刷新单次约多 18 毫秒。单次读数无法确定小画板延迟的稳定变化。

混合文档含 85% 几何图形、5% 便签和 10% 压感笔迹。视口为 1280 × 800，DPR 1，关闭 GPU 加速。计时区段包括 Chromium 原生滚动手势、100% 局部视图、全图缩放以及抬笔后的保存。每次手势结束后再观测 500 毫秒，覆盖延迟绘制。帧间隔来自 requestAnimationFrame，丢帧率按 60 Hz 节拍估算。两台设备为逻辑隔离的真实浏览器上下文，网络为本机回环。公网 RTT、物理显示屏扫描和 Apple Pencil 的端到端延迟需在实机测量。[逐次原始数据与构建摘要](../evidence/performance/browser/matrix.json)

在 10 万混合对象上，全图滚动输入到第二次动画帧的 P95 从 832.6 ms 降至 34.8 ms。单次动作结束后，优化版两轮中最高一次出现了 33.3 ms 的尾帧。把测试进程树的 RSS 加总，峰值从约 2,788 MiB 降至 2,099 MiB，这个读数包含至少两个浏览器上下文、服务和测试进程，也可能重复计算共享页。

## 密集笔迹的三轮调优

在同一张含 4,096 条可编辑笔迹、327,680 个采样点的画板上测试。密集视野约有 1,000 条笔迹，稀疏视野有 16 条。各笔包含 32 至 128 个样本，保留压力、倾角、扭转和切向压力。

| 实现 | 密集普通笔，输入至实际填充 P95 | 连续书写帧间隔 P95 | 抬笔至独立 SQLite 观察到提交 |
| --- | ---: | ---: | ---: |
| 原版，两轮 | 180.2 / 249.9 ms | 183.4 / 266.7 ms | 中位 399 / 368 ms |
| 第一轮，缓存已提交的可见画面 | 16.3 / 16.1 ms | 133.3 / 150.0 ms | 中位 250 / 265 ms |
| 第二轮，向缓存增量追加顶层笔迹 | 16.4 ms | 16.7 ms | 中位 155 ms |

第一轮消除了移动笔尖时重画全部旧笔迹的开销。抬笔仍会使缓存失效，第二轮只将顺序可证明的新笔迹合入底图。并发编辑改变了排序，或者用户撤销、修改旧对象时，缓存会重新构建。

第三轮处理荧光笔。它必须画在普通笔迹和文字下方，直接叠加会遮盖前景。现在只重绘受影响像素矩形内的对象，沿用原来的叠放和混合顺序。密集荧光笔从输入到填充的 P95 从 201.8 ms 降至 16.2 ms，连续书写帧间隔 P95 从 200.0 ms 降至 16.8 ms。独立遮挡测试验证了 2,280 个不透明前景像素保持原色，周围 2,076 个像素出现荧光标记；落笔期间、抬笔及刷新后的截图一致。与原版整体栅格对照，密集区域 402,500 个像素中有 20 个像素的单通道差超过 8/255，主要轮廓与颜色保持一致。导出沿用矢量绘制。[逐帧数据、输入样本和像素校验](../evidence/performance/ink-scale.json)

最后又把同类画板压到接近 32 MiB 配额。8,192 条笔迹共含 655,360 个采样点，其中 4,000 条、约 32 万点同时可见。相同的一个 16 事件笔势，书写帧间隔 P95 从 699.9 ms 降到 16.8 ms；指针事件到 Canvas 填充调用的中位耗时从 573.9 ms 降到 15.2 ms；抬笔到 SQLite 可读从 1,284 ms 降到 139 ms。每版各一次，定位的是极限负载下的瓶颈。两版均通过压力、倾角和刷新恢复检查。

## 存储、同步和画布 MCP

| 独立测试 | 原版 → 调优版 |
| --- | ---: |
| 50,000 便签，完整快照 HTTP 中位 | 441.0 → 64.5 ms |
| 50,000 便签，从零修订号追赶 HTTP 中位 | 496.8 → 68.6 ms |
| 两台设备同时冷读，服务进程内存高水位 | 355.8 → 188.8 MiB |
| 50,000 便签，支持 gzip 的客户端下载 | 24,140,828 → 1,220,844 字节 |
| 50,000 混合对象，6 人并发写入 P95 | 5.59 → 3.28 ms |
| 100,000 对象，MCP 单 ID 读取中位 | 2.64 → 0.07 ms |
| 100,000 对象，MCP 整板分页中位 | 19.29 → 0.12 ms |

服务端从同一个 SQLite 读事务输出已校验的 JSON，对大响应协商 gzip。两个记录的小增量仍在约 0.4 ms。1,024 条记录的批量写入中位为 12.13 → 13.90 ms，这条写入路径保留了原有校验和持久化成本。各子系统基准独立运行，不能把不同测试的毫秒值相加。六位编辑者在同一初始修订号上各改 120 个不同对象，另有两位读者同时读取。服务重启后重算所有 50,000 个对象，全部 720 次确认写入均存在。[服务端原始样本](../evidence/server-scale.json) · [并发写入与重启校验](../evidence/multiwriter-scale.json)

浏览器对已缓存画板仅请求修订后的增量，IndexedDB 以快照和逐对象变更记录保存。12,000 对象单笔编辑曾触发整板读写；现在只写变更对象与版本。冷启动保存 3.51 MB 基础快照时，主线程同步进入 IndexedDB put 的时间从 43.5–56.7 ms 降到 0.2–0.3 ms。该数字只含发起持久化操作时的主线程工作，实际事务另行等待。离线重开、旧缓存迁移、两标签页抬笔即关和冲突恢复均有覆盖。[浏览器缓存测量](../evidence/performance/blob-profile.json)

50,000 对象的独立渲染测试把点击命中 P95 从 3.34 ms 降至 0.01 ms，移动单个对象并提交画面从 8.0 ms 降至 0.3 ms。1,000、10,000 和 50,000 对象的稀疏与密集视野共六组像素摘要逐字节一致。[调优前](../evidence/performance/renderer-before.json) · [调优后](../evidence/performance/renderer-after.json)

渲染和点击共用增量空间索引。普通笔、荧光笔、贝塞尔曲线、旋转对象和连接线保留原有层级语义。MCP 直接通过对象 ID、选区或视野读取，分页缓存随文档变化失效。MCP 时间含真实浏览器中 MCP 帧的解析、工具分发及本地画布查询；模型生成、网络和 SQLite 写入各自单独测量。[MCP 请求样本](../evidence/performance/mcp-scale.json)

## 容量边界

在最终发布包上另做一轮 **250,000 个可编辑矩形** 的 Chromium 实测。对象分布在不同位置，持久化对象共 33,057,916 字节。首次打开耗时 4.84 秒，全图（5%）和局部（100%）平移的帧间隔 P95 分别为 16.7 ms 和 16.8 ms。原生笔输入产生 16 个压力和倾斜采样点，改变了 444 个画布像素。第二个设备随后冷开用了 4.98 秒，刷新 4.26 秒，逐条核对 25 万个原始对象及新增笔迹全部一致。此项为单轮测试，两台设备依次打开，进程树 RSS 峰值 1,856 MiB。[单轮测量记录](../evidence/compact-browser-250000.json) · [浏览器截图](../evidence/compact-browser-250000.png)

- 在 32 MiB 文档对象配额内，服务端实存 292,724 个紧凑矩形。再写一个 116 字节的记录会被拒绝，修订号和既有内容保持一致。重启后只读设备完整读回这 292,724 个对象。
- 在本次含完整压力和双轴倾角的笔迹分布下，可提交 8,616 条笔迹、689,280 个采样点，共占 33,553,710 字节。下一笔触发配额。相同表示下，单张画板放不下 100 万个此类采样点。
- 首次打开仍需要取得和解析完整快照。屏幕像素数、视口中实际对象密度、附件及显示比例都会改变交互成本。大尺寸视口的缓存有 600 万物理像素上限。当前实现为单服务进程 + 持久化 SQLite。

完整工程含固定前后版本的还原补丁、数据生成器、看门狗和校验脚本。[复现说明](../qa/performance.md)

## 发布回归

最终源码通过严格 TypeScript 和格式检查、57 项 Bun 测试以及 20 个完整 Chromium 功能场景。期间源代码和生产前端摘要保持一致。参考图界面约定指标为 98.73%。Linux WebKit 26.5 与 Chromium 双向编辑、刷新恢复也已验证。Luna 的 Chat 验收从空白画板开始，经过 13 次真实模型请求，生成 61 个可编辑对象，其中含 8 条笔迹，导出再导入后逐项一致。[功能回执](../evidence/acceptance.json) · [Luna 录屏回执](../evidence/chat-luna.json)
